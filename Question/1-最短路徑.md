# 需求描述
使用者想要知道 以目前 osm 匯入的資料可以實作最短路徑?

# 結論（2026-11-20）

**可以，但現有 `roads` 表不能直接用**，需在 Lua 加一張路網專用表再建拓撲。

## 現況盤點

| 項目 | 狀態 |
|---|---|
| 道路資料 | `roads`（kind = highway）82.8 萬條 way、19.2 萬 km，涵蓋汽車到步道 |
| pgRouting | 4.0.1 已隨 PostgreSQL 安裝（`libpgrouting-4.0.dll`），**尚未 `CREATE EXTENSION`** |
| 單行道 | ✅ `oneway`（direction 型別，1／-1／0），7.0 萬條 |
| 路口拓撲 | ❌ way 未在路口切段：台北 101 周邊 2 km 抽樣，39% 的 way 端點落在另一條 way 中段 |
| OSM node id | ❌ 未保存 → 無法用「共用節點」精確切段 |
| 通行限制 | ❌ 未匯入 `access`／`motor_vehicle`／`maxspeed`／`junction` 等 tags（roads 無 tags 欄） |
| 轉向限制 | ❌ `type=restriction` relation 未匯入 |

## 建議做法（pgRouting）

1. `taiwan.lua` 新增 `routing_ways` 表：只收可通行的 highway，保存 `object.nodes`（node id 陣列）、`oneway`、`maxspeed`、`access`、`junction` 等；`roads` 維持出圖用途不動。
2. SQL（新 `06_routing.sql`）：以「被 ≥ 2 條 way 使用的 node」切段 → `routing_edges(id, source, target, cost, reverse_cost, geom)`，source／target 直接用 OSM node id。
   **不要用幾何交點切段**（`pgr_separateCrossing` 等）：高架橋、地下道在 2D 會相交但實際不相通，用 node 才正確。
3. cost 依車種：汽車用長度 ÷ 速度（maxspeed 或依道路等級預設），步行用長度；單行道 `reverse_cost = -1`。
4. 查詢：`pgr_bdAstar`（或 `pgr_dijkstra`）＋起訖點 `ORDER BY geom <-> point` 找最近節點；全台 ~100 萬邊，長距離查詢需以起訖點 bbox 限縮子圖。
5. 對外 API：Martin 只出圖磚，不適合做路徑查詢 → 需一個小 API（例如 FastAPI，回傳 GeoJSON），前端以 GeoJSON source 疊上路線。

## 自架 OSRM PoC（2026-11-20，開發機）

環境：Docker Desktop 29.9.3（WSL2，VM 12 CPU／8.2 GB）、`ghcr.io/project-osrm/osrm-backend:v6.0.0`、MLD 演算法、資料 `taiwan-261112.osm.pbf`（313 MB）。

### 建置（`C:\gis\osm\osrm\{car,foot}\`，各放一份 PBF）

| profile | extract | partition | customize | 尖峰記憶體 | 資料大小 | 執行時記憶體 |
|---|---|---|---|---|---|---|
| car | 60 s | 40 s | 18 s | 1.9 GB | 1.1 GB | 0.8 GB |
| foot | 86 s | 31 s | 9 s | 2.5 GB | 1.4 GB | 0.9 GB |

```powershell
$img = 'ghcr.io/project-osrm/osrm-backend:v6.0.0'
docker run --rm -v C:\gis\osm\osrm\car:/data $img osrm-extract -p /opt/car.lua /data/taiwan.osm.pbf   # foot 用 /opt/foot.lua
docker run --rm -v C:\gis\osm\osrm\car:/data $img osrm-partition /data/taiwan.osrm
docker run --rm -v C:\gis\osm\osrm\car:/data $img osrm-customize /data/taiwan.osrm
docker run -d --name osrm-car --restart unless-stopped -p 127.0.0.1:5000:5000 -v C:\gis\osm\osrm\car:/data $img `
  osrm-routed --algorithm mld --max-table-size 100 --max-trip-size 25 /data/taiwan.osrm      # foot → 127.0.0.1:5001
```

| 開車 三峽 → 板橋車站 | 14.8 km／19 分／4 ms | 14.8 km／19 分／700 ms | 0.0% |

| 步行 三峽 → 板橋車站 | 13.7 km／166 分／6 ms | 14.6 km／195 分／691 ms | −5.9% |

- 開車與 OSRM 官方 demo（同為預設 `car.lua`）幾乎一致；步行差異來自 FOSSGIS 使用自訂 foot profile（速度較慢、路徑偏好不同），非資料錯誤
- 本機查詢 4–12 ms（含全台長途），公開服務 0.7–2.3 s 且有用量限制

### PoC 結論

- 台灣資料量對 OSRM 很小：兩個 profile 建置合計約 4 分鐘、執行時共約 1.7 GB 記憶體、磁碟約 2.5 GB
- 待決定：正式機執行方式（Docker Desktop 需登入才啟動／WSL2 + docker-ce／Linux 主機）、對外網址（需 named tunnel → 網域）、機車 profile（預設 car.lua 會走國道）

## 替代方案

若需要長途快速查詢、轉向限制、導航指示，改用專用引擎（OSRM／Valhalla／GraphHopper）直接讀同一份 `taiwan.osm.pbf`，不經 PostGIS；代價是多一個服務要維運（Windows 上多半以 Docker 執行）。
